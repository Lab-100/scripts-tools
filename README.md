# scripts-tools

**INVR-Tools** — реестр версий инструментов оркестрации. Единый канон: здесь лежат
все версии всех инструментов, а потребители получают их через локер `resolve-tools`
и вызывают плоские шимы.

Дистрибутор, который ставит этот реестр на машину: [`devstation-deploy`](../devstation-deploy).

## Структура

```
registry/
  _registry.json          манифест реестра (список инструментов и latest)
  <tool>/
    latest.txt            указатель на актуальную версию
    <version>/
      tool.json           метаданные инструмента
      <entry>             исполняемый файл (или несколько)
<tool>.ps1, <tool>.cmd    плоские шимы в корне (генерируются локером)
tools/ci/              скрипты непрерывной проверки репозитория (не часть реестра)
artifacts/             отчёты проверок (локальный запуск и CI), в .gitignore
project.json              манифест проекта: владелец, режим, требуемые диапазоны
```

Версии неизменяемы. Правка инструмента — это **новая версия** в новом каталоге;
старые каталоги не трогаются. Актуальная версия переключается правкой `latest.txt`.

| Инструмент | Назначение |

| `mcp-watchdog-guardian` | сторож над демоном-стражем: сам поднимает его при зависании (HKCU Run) |

| `opencode-status` / `opencode-monitor` | статус и мониторинг opencode |
| `opencode-restart` | перезапуск opencode с подъёмом демона-стража и ожиданием готовности MCP |
| `opencode-plugins` | установка плагинов opencode |
| `browsertool` | headless-браузер (драйвер + протокол на 127.0.0.1:8123) |
| `doc-extract` | извлечение текста/таблиц из документов пулом OCR-провайдеров с судьёй |

## Использование

Локер читает `project.json` проекта, разрешает диапазоны версий, скачивает нужное
из этого реестра и создаёт junction-линки `<проект>\tools\<tool>` плюс шимы.

```powershell
# развернуть инструменты в проект и сгенерировать шимы
.\resolve-tools.ps1 link -Project C:\path\to\project -GenerateShims

# что установлено / что доступно
.\resolve-tools.ps1 status -Project C:\path\to\project
```

Корень реестра переопределяется переменной `INVR_REGISTRY`, иначе определяется
от расположения шима: `$PSScriptRoot\registry`, затем `$PSScriptRoot\tools\registry`.
Так один и тот же шим работает и в клоне реестра, и в плоском каталоге
инструментов, и в раскладке дистрибутора, где шимы лежат уровнем выше реестра.
В репозитории не осталось машинных путей — шимы переносимы.

### Переменные окружения

| Переменная | Назначение | Дефолт |
|---|---|---|
| `INVR_REGISTRY` | корень реестра (где лежит каталог `registry`) | определяется от расположения шима |
| `INVR_TOOLS_ROOT` | корень инструментов (каталог с шимами и `registry`) | выставляется шимами, создаваемыми `resolve-tools` |
| `INVR_NODES_FILE` | файл состояния узлов монитора | `<tools-root>\monitor\state\nodes.json` |
| `INVR_WATCHDOG_STATE_FILE` | снимок состояния демона-стража | `<tools-root>\mcp-watchdog\state\current.json` |
| `INVR_LAB_DIR` | каталог пула Lab100 | `Lab100` рядом с корнем инструментов |
| `INVR_OLLAMA_MODELS_DIR` | каталог моделей Ollama | `OllamaModels` рядом с корнем инструментов |
| `INVR_LOG_DIR` | каталог журналов демонов | `%USERPROFILE%\.devstation\logs` |
| `INVR_ROLLBACK_ROOT` | корень каталога откатов | первый несистемный диск, затем `rollback-root.txt` |
| `INVR_VM_ROOT` | каталог виртуальных дисков Hyper-V | первый несистемный диск |
| `DOCKER_WSL_DATA_DIRS` | дополнительные `ext4.vhdx` Docker WSL через `;` | не перечисляются (сканируется только штатный `%LOCALAPPDATA%`) |
| `HERMES_EXE` | путь к исполняемому файлу Hermes | `~/.local/bin/hermes.exe` |
| `HERMES_PROJECT_DIR` | рабочий каталог Hermes-агента | каталог `hermes-project` рядом с инструментами |
| `BROWSERTOOL_PORT` | порт headless-браузера | `8123` |
| `BROWSERTOOL_CHANNEL` | канал браузера (стабильный/бета) | стабильный |
| `OLLAMA_HOST` | адрес локального сервера Ollama | `127.0.0.1:11434` |

Приоритет везде одинаковый: параметр команды → переменная окружения →
переносимый дефолт.

## Приватные настройки и секреты

**В коде и в этом репозитории нет ни ключей, ни паролей, ни личных путей.** Принципы:

- Ключи API читаются **только из переменных окружения** (`Get-EnvStrict`).
  В коде нет значений, в репозиторий не попадает ничего секретного.
- Пути машинных каталогов задаются переменными окружения или параметрами
  (`INVR_REGISTRY`, `INVR_ROLLBACK_ROOT`, `HERMES_EXE`, `BROWSERTOOL_PORT` и др.),
  в коде — переносимые дефолты.
- Персональные настройки хранятся в файлах `*.local.json` и `config.local.json`.
  Они в `.gitignore` и в публичный репозиторий не попадают.
- Региональные и машинные особенности в публичном коде описаны нейтрально
  («недоступен в некоторых регионах»), без привязки к конкретной стране.
- Каталоги версий в `registry/` содержат только код: рабочие `state/`, `logs/`,
  `requests/` и `*.pid`, которые инструменты создают рядом с собой при запуске
  без `-RuntimeDir`, исключены в `.gitignore` и в репозиторий не попадают.

Поэтому репозиторий можно читать, форкать и ставить на любую машину: приватное
остаётся в локальной копии и в окружении, а в общий код попадает только
переносимая логика.

## Непрерывная проверка (CI)

`.github/workflows/ci.yml` срабатывает на `push` в `main`, на `pull request`
в `main` и по ручному запуску. Три независимые проверки:

| Проверка | Что делает | Падает при |
|---|---|---|
| PSScriptAnalyzer | статический анализ всех `.ps1` по явному набору из 40 разрешённых правил | любой находке |
| Синтаксис и Pester | разбираемость всех `.ps1`/`*.psm1`/`*.psd1` парсером PowerShell; Pester запускается, если появится каталог `tests` | ошибке синтаксиса, провале тестов |
| Поиск секретов | сканер типовых секретов по всему репозиторию | любой находке |

**Pester-тестов в репозитории нет**, и выдумывать их не стали: вместо них CI
проверяет синтаксис всех PowerShell-файлов. Шаг с Pester в workflow остаётся и
сработает автоматически, как только появится каталог `tests` с файлами
`*.Tests.ps1`.

Те же проверки запускаются локально тем же кодом:

```powershell
# статический анализ (без -FailOnFinding всегда код 0: только отчёт)
pwsh -NoProfile -File .\tools\ci\invoke-psscriptanalyzer.ps1 -FailOnFinding

# проверка синтаксиса
pwsh -NoProfile -File .\tools\ci\invoke-syntax-check.ps1

# поиск секретов
pwsh -NoProfile -File .\tools\ci\scan-secrets.ps1
```

Требования: `pwsh` 7, модуль `PSScriptAnalyzer` (для CI ставится на лету),
`Pester` 5.5+ (только когда появятся тесты). Отчёты (`pssa-report.ndjson`,
`syntax-report.ndjson`, `summary.txt`) кладутся в `artifacts/` — каталог в
`.gitignore`, в GitHub отчёты приезжают артефактами сборки.

Набор правил анализатора зафиксирован под текущий код намеренно: версии
инструментов в реестре неизменяемы, поэтому подогнать существующие версии под
правила анализатора нельзя. Список отключённых правил с причинами — в шапке
`tools/ci/invoke-psscriptanalyzer.ps1`.

## Проверка секретов

`tools/ci/scan-secrets.ps1` сканирует репозиторий на типовые секреты: ключи
API известных провайдеров, токены и пароли в коде и конфигурации, приватные
ключи, строки подключения с учётными данными.

Скрипт **никогда не печатает и не записывает найденные значения** — в вывод и
в отчёт попадают только путь, номер строки, тип находки и описание правила.
Ненулевой код возврата при находках позволяет вызывать его из CI.

```powershell
# весь репозиторий по умолчанию
pwsh -NoProfile -File .\tools\ci\scan-secrets.ps1

# только каталог реестра + отчёт CSV
pwsh -NoProfile -File .\tools\ci\scan-secrets.ps1 `
    -Path .\registry -Report .\artifacts\secrets\findings.csv
```

Отсекаются ложные срабатывания: упоминания имён переменных окружения
(`GEMINI_API_KEY`, `GetEnvironmentVariable('FIRECRAWL_API_KEY')`) секретами не
считаются, правила срабатывают на литералы значений; отбрасываются
плейсхолдеры (`sk-...`, `YOUR_*`, `<...>`, `${...}`, `changeme`, `redacted`,
`example.com`, `localhost`), пустые и короткие значения.

## Требования

- Windows 10/11, PowerShell 7 (`pwsh`)
- Node.js 18+ — только для `browsertool`
- Ollama — для `llm-mcp` и локальных субагентов
