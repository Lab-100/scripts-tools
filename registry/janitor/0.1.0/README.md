# Чистильщик мусора (janitor) v0.1.0

Утилита на Node.js (ESM, без внешних зависимостей) для безопасной уборки
временных и устаревших файлов в каталогах opencode.

**Главный принцип — безопасность по построению.** По умолчанию работает
**сухой прогон**: ничего не удаляется и не перемещается. Реальное действие
возможно только с явным флагом `--yes`, только через карантин и только если
файл прошёл **все** гварды.

## Модель решения

Вердикты:

- `keep` — не трогать;
- `candidate` — можно переместить в карантин (при `--yes`);
- `delete` — физически снести из карантина по сроку (команда `purge`).

Удаление — это **конъюнкция гвардов** (достаточно одного «нет» → `keep`):

1. **protect** — файл не в защитном списке (`config.protect`, по маскам).
   deny-доминирование: protect сильнее любого правила.
2. **git** — файл не отслеживается git (сверка с `git ls-files -z`).
   Не git-репозиторий → считается «не под git».
3. **rule** — сработало известное правило из `rules.json`. Нет правила → `keep`.
4. **owner** — владелец мёртв (для правил с `requireDeadPid`): PID из имени файла
   или из содержимого lock-файла, проверка `process.kill(pid, 0)` (EPERM = жив).
   PID не определён → `keep`.
5. **busy** — файл не занят (пробное `fs.openSync(path, 'r+')`;
   EBUSY/EPERM/EACCES → `keep`).
6. **age** — возраст `mtime` старше порога правила (`keepDays` / `minAgeMin`,
   по умолчанию 7 суток). Если задан `rotateAtMb` — дополнительно требуется
   размер больше порога ротации.
7. **immunity** — нет иммунитета по обращениям (см. ниже).
8. **port** — сервис-владелец не держит порт (для правил с `servicePort`).

Дополнительно: `requireOriginal` (для `config-backup`) — оригинал без `.bak`
должен существовать. Любая ошибка на файле → `keep`, проход продолжается.

## Иммунитет по обращениям (refs)

Хранилище — SQLite (`refs.db`, WAL) через `node:sqlite`; журнал — `actions.jsonl`.

- Счётчик с затуханием: `w = hits · decay^(дней с lastSeen)`, окно `windowDays`.
  События вне окна отбрасываются.
- Таблицы: `counters`, `whitelist`, `edges`, `meta`.
- Источник обращений №1 (реализован): **статический граф ссылок** по содержимому
  файлов (`require`, `import/export ... from`, `{file:...}`, `include`, `extends`,
  относительные/абсолютные пути). Новое ребро `src→dst` = +1 обращение к `dst`.
- Источник №2 (заглушка, выключен): **ETW Kernel-File** (реальные события доступа).
  Требует прав администратора; в v0.1.0 не реализован (`config.refs.etw=false`).
- **Иммунитет**: `w ≥ theta` И `lastSeen` в окне И есть входящее ребро.
  Иммунитет только повышает вердикт до `keep` и никогда не разрешает удаление.
  `theta` — порог затухания (вес `w ≥ theta` → иммунитет); `windowDays` — лишь
  окно учёта обращений, а не срок иммунитета.
- Обращения самого чистильщика не учитываются: каталог `janitor/**` пропускается,
  и он же в protect.

`theta` (по умолчанию 10) — **калибровать по статистике** командой `status`.

## Корни сканирования (roots)

`config.json` → `roots` — список каталогов, которые чистильщик обходит.

- **Пустой или отсутствующий `roots`** → берутся корни по умолчанию:
  1. каталог конфигурации opencode (тот, где лежит `janitor/`);
  2. рабочий каталог opencode во временной папке (`TEMP`/`TMP`, иначе
     `%USERPROFILE%\AppData\Local\Temp`).
- **Непустой `roots`** → используется как есть; приоритет явного списка из
  конфига выше корней по умолчанию.
- Элементы `roots` раскрывают переменные окружения: `%VAR%`, `${VAR}`, `$VAR`
  (например, `%USERPROFILE%\.config\opencode`). Неизвестная переменная
  остаётся как есть — опечатка видна сразу. Относительный путь отсчитывается
  от каталога конфигурации (а не от текущего рабочего каталога процесса:
  MCP-сервер запускает CLI без задания cwd).
- Персональные абсолютные пути в конфиге не нужны: `"roots": []` — переносимый
  вариант по умолчанию, одинаковый на любой машине.

Фактические корни видны в выводе `status` и `scan` (строка «Корни: …»).

## Команды

```
node janitor.mjs scan                 # сухой прогон: таблица решений и сводка
node janitor.mjs scan --all           # показать также все keep-строки
node janitor.mjs clean                # план перемещения в карантин (без --yes)
node janitor.mjs clean --yes          # реально переместить candidate в карантин
node janitor.mjs purge                # план удаления из карантина (без --yes)
node janitor.mjs purge --yes          # удалить из карантина старше quarantineDays
node janitor.mjs restore <id|path>    # вернуть из карантина (нужен --yes)
node janitor.mjs status               # метрики
node janitor.mjs explain <path>       # пошаговые гварды для пути
node janitor.mjs compact              # компакция хранилища
node janitor.mjs --watch [--interval-min N]   # фоновый режим (одиночный экземпляр)
```

Флаги: `--dry-run` (принудительный сухой прогон), `--yes` (разрешить действие),
`--watch`, `--interval-min N`, `--all`.

`--watch` защищён файлом `janitor.lock` (PID + время старта). Замок считается
протухшим только если PID мёртв или не читается; при живом PID второй экземпляр
отказывается стартовать, а владелец обновляет замок (heartbeat) на каждом тике.

## Где хранятся данные

| Файл | Назначение |
|------|-----------|
| `config.json` | конфигурация (корни, пороги, protect) |
| `rules.json` | правила уборки |
| `refs.db` | SQLite: счётчики, whitelist, рёбра, метки |
| `actions.jsonl` | журнал действий (append-only) |
| `quarantine/<дата>/<путь>` | карантин |
| `janitor.lock` | замок одиночного экземпляра |

## Что НИКОГДА не удаляется

- Каталоги `node_modules`, `.git`, `secrets`, `janitor` не обходятся вовсе.
- Список `protect`: `secrets/`, `node_modules/`, `state.json`, `opencode.db*`,
  `*.git/`, `auth.json`, `bridge/inbox/`, `bridge/outbox/`, `*.lock`, `janitor/`.
- Всё, что отслеживается git, и всё, для чего нет известного правила.
- Файлы вне `roots`.

## Как расширять правила

Добавьте объект в `rules.json`:

```json
{ "id": "my-rule", "glob": "**/*.myext", "kind": "temp",
  "requireDeadPid": true, "minAgeMin": 120 }
```

- `glob` — маска (неякорная ищется на любой глубине);
- `keepDays` / `minAgeMin` — порог возраста;
- `requireDeadPid` — требовать мёртвого владельца (PID в имени/lock);
- `requireOriginal` — требовать наличия «оригинала» (до `.bak`);
- `rotateAtMb` / `keepMb` — порог размера для логов;
- `servicePort` — порт сервиса-владельца (занят → keep).

Порядок правил важен: срабатывает первое совпавшее.

## Ограничения v0.1.0

- ETW Kernel-File не реализован (заглушка; нужны права администратора).
- `theta` не калиброван — подбирается по `status`.
- Обращения в статическом графе учитываются один раз (по новым рёбрам);
  повторные прогоны не инфлятируют счётчик.
- Правило `quarantine-purge` в `scan` перекрывается protect (`**/janitor/**`);
  карантин обслуживается командой `purge`.
- Правило `test-locks` (**/test-*.lock) перекрывается защитой `**/*.lock`
  в `config.protect`: lock-файлы намеренно не удаляются. Правило сохранено
  для совместимости, но ни один файл по нему не будет перемещён.
